# 0.1.6 言笑／辅佐修复与早夭调查

## 已修复：言笑

旧bgm-ai.lua中，选择受控队友后仅设置了局部target和use.card，但追加use.to的代码被错误嵌套在“给自己言笑”的分支内。技能实际执行在目标列表为空时默认作用于自己，因此看起来只会自贴。旧策略又以手牌数大于1限制帮助队友，即使只有的一张方片能解控也不援助。尾部错位的end还把安娴的AI回调定义嵌在言笑使用回调里，直到使用言笑才注册。

LEGACY-AI-003补丁：优先选有判定牌、尚无smile保护的友方，把所选目标加入use.to；允许使用最后一张方片；随后考虑自救；没有需要处理的判定牌时不消耗方片盲目自贴。方片按保留价值排序。把安娴注册恢复到加载时执行，保持安娴回调内容不变。原始素材不修改，补丁仅应用到运行资源副本。

## 已修复：辅佐

旧wisdom-ai.lua直接写死return cancel，并无@fuzuo_card的响应实现；C++也未向选择阶段传递实际PindianStruct。因此AI没有数据判断要援助谁、需要几点，更不会给出干预牌。

C++传入实际拼点数据。LEGACY-AI-004补丁根据AI感知的敌友关系，仅在援助能改变友方对敌方的结果时，选保留价值较低、点数小于8的手牌并返回实际实体牌。发起方必须严格大于对方；防守方打平即可使敌方发起者失败。增量不足、1点牌加成为0、8点及以上、双方均为友方、已用于本次拼点的牌均不会使用。响应后清除本次缓存。临时加点卡通过deleteLater清理，不跨线程设置QObject父对象。

04-green.log曾暴露开发中的响应类型问题：$id返回的是点数0的DummyCard。已改为实体卡号字符串，并用真实原装牌验证实际加点和胜负；该中间失败没有算作通过。首次测试构造参数编译错误见01-red-build.log，修正后才运行RED测试。02-red.log确认原版言笑两个场景、辅佐两个可获益场景失败。

## 未定位：早夭

用户明确报告超过13张、双将下都未触发，不把用户报告归因于“正好13张”。检查实际代码与18个定向用例仍未复现：04p／10pz两模式，13／14／16张，曹冲单将、曹冲＋曹操、曹操＋曹冲。通过真实ServerPlayer::play的弃牌、结束、NotActive阶段和RoomThread注册／调度，14/16张均清空并失去1体力，13张保持；不是直接调用早夭函数代替调度。

这些用例不能代表所有双将、其他玩家技能或完整实战状态，没有修改早夭规则，也没有宣称已修复该报告。新增本地有界诊断：每次曹冲进入PhaseChange时，记录前后真实手牌数、体力、主副将、模式、技能有效性、注册状态、执行过的技能、提前中断者。路径为应用数据目录下diagnostics/zaoyao.jsonl，超过约1MiB时从头记录。只记录计数与调度，不记录手牌牌面、不上传；写入失败不影响游戏。下一次原局异常可用于区分显示不同步、未进入结束阶段、技能失效或调度中断。
